# AGENTS.md

SkillUp Forever is a WoW: Forever addon (Interface 16001) that adds skill-up chances, costs and a
levelling route to the Professions window. It requires ForeverCore (`## Dependencies: ForeverCore`,
`required-dependencies` in `.pkgmeta`), the standalone addon every Forever addon needs: the tracker column, the
report window, leaderboards, the error journal and debug log, the settings chrome and the family page are core's
alone. Players install the zip the BigWigs packager builds on a `v*` tag, and the stores install ForeverCore with it.

## Commands

```sh
python3 tools/doctor.py   # first on a new machine: every tool pin below, with a fix for each problem
export FOREVER_CORE=~/forever-core   # or the checkout of tools/forever-core.txt's ref, beside this one
stylua --check .
ruff format --check tools && ruff check tools
luacheck .
tools/typecheck.sh
for s in tests/*_spec.lua; do luajit "$s" || exit 1; done
luajit tests/bench.lua   # CPU timings in the harness; asserts nothing, but must run to the end
python3 tools/changelog.py --check
python3 tools/check_api_docs.py   # every name Core/API.lua publishes is in docs/api.md, with its minor history
python3 tools/check_generated.py   # regenerate in a disposable tree; require fresh, byte-stable Data/*.lua
python3 tools/forever_tools/credits.py --check   # Data/Credits.lua and both thanks blocks are current (WFA-31)
python3 tools/check_screenshots.py   # an image older than its sources; --record after tools/screenshots.py
python3 tools/check_menu_scroll.py # menus built from a list scroll (WFA-36); CI runs it in core-shared
```

CI's `package` job builds the zip with the release's packager without uploading (`-d -z`) and runs
`python3 tools/check_package.py` on its output: every loaded file ships, no development folder does, a licence file and
THIRD_PARTY.md ship with README's `## Credits` and THIRD_PARTY's `## Players` (WFA-10, WFA-31), and the
specs pass on the packaged files.

The same gate CI runs, plus actionlint, zizmor and gitleaks on the workflows and history.
`.github/workflows/speedpatrol.yml` times `tests/bench.lua` on every pull request against its base branch and fails on
a regression (`.speedpatrol/instructions.md`).
Every version needs a `CHANGELOG.md` entry (prose, bold-lead bullets) before its `v*` tag: the release
publishes it as the notes.

## Layout

- `Data/*.lua` — generated by `tools/gen_*.py` (see `tools/README.md`); never hand-edit. A daily
  workflow (`.github/workflows/refresh-data.yml`) runs `tools/bump_pins.py`, which moves each generator pin
  to its newest upstream (Forever and Classic Era builds, the LibPeriodicTable file),
  regenerates, runs the specs, opens a PR on `data/refresh` and approves its CI and Speedpatrol runs, which GitHub
  holds for a PR opened by `GITHUB_TOKEN`. A scheduled run that fails is re-run once by
  `.github/workflows/retry-refresh.yml`, and one that fails again opens or comments on the one "Data refresh failed" issue. The classic-db pin is a waiver below and stays by hand.
- `Integrations/Questie.lua`, `Integrations/AtlasLoot.lua`: the only readers of the player's QuestieDB and
  AtlasLoot, through their public tables. `Integrations/Catalogue.lua` joins them into `ns.Catalogue`: a
  profession's scroll sources, vendors, quests and NPC places, built on first ask, kept for the session (never
  saved) and read through one queue of at most 32 records or 1 ms a frame. Everything else asks the catalogue,
  and treats nil as "not read yet or not installed". A vendor seen selling a reagent or scroll at its own window
  is saved (`ns.db.sellers`) and joins the catalogue with where the player stood. Nothing from either addon is copied into the repo, the
  zip or a test: fixtures are the synthetic `Client.QuestieDB` and `Client.AtlasLoot` in `tests/client.lua`.
- `Core/Core.lua` registers the addon's shared services once at load (`ns.core`), and the tracker section it
  attaches lives in `UI/Shopping.lua` with the shopping routes. Everything shared (tracker, report, leaderboards,
  journal, log, settings page, family page, minimap button, context menu) is ForeverCore's, read from the
  `ForeverCore` global: never copy one of its files here.
- `Core/Model.lua`, `Integrations/Prices.lua` — the headless-testable maths; the UI files call them.
  `Integrations/Prices.lua` also holds the sub-craft cost: a reagent a known recipe makes is priced at the
  cheaper of buying and crafting it, three levels deep, memoised and cycle-safe.
- `Core/Live.lua`: the client's own recipe read, the live grey threshold, the skill points one craft grants
  and the tool and station a recipe needs. One scan covers a burst of profession events, and the bundled
  thresholds stay the fallback, with the live grey replacing only the fourth number.
- `Core/Plan.lua` — the levelling plan, in base skill with trainer requirements resolved. The route page,
  tracker, public API and trainer window draw what it returns; none reads the modifier or trainer tables.
- `Core/Changes.lua` — what goes stale when something changes. A writer calls `ns.Changed(kind)` and game events
  arrive on its one frame; only it decides which caches drop and which views redraw. No file clears or redraws
  another's: own a cache or view with `ns.WhenStale`, do per-event work with `ns.WhenEvent`.
- `Locales/` — `enUS.lua` makes `ns.L`, keyed by the English phrase; a translation is `Locales/<locale>.lua` listed
  after it in the TOC (`Locales/README.md`). Player-visible text is a whole `L["..."]` phrase (format strings
  included); after changing one, `python3 tools/phrases.py > Locales/phrases.txt`. `tests/locale_spec.lua` checks
  both, and that no packager localization keyword (which fails the release) is in the tree.
- `docs/curseforge.md` — the store description, pasted into CurseForge and Wago by hand.

## Rules

- Lua 5.1 in the game's sandbox: no `require`. The client loads the files `SkillUpForever.toc` lists, in
  that order, each receiving `local addonName, ns = ...`; a new file goes in the TOC or never runs.
- The specs are a headless harness with stubbed client APIs. `tests/client.lua` is the shared stub client: it
  loads ForeverCore from `FOREVER_CORE` first, then the TOC in order, and a spec over it sets what the client
  holds, not an `ns` function. `tests/forever_core.lua` is the one place that finds the checkout (`FOREVER_CORE`,
  else `../forever-core`); `tools/forever-core.txt` names the ref CI checks out. Anything the specs
  cannot reach (frames, menus, tooltips, the tracker) is checked in game: check them in the headless client (forever-core's `wow-forever-addon/in-game.md`) and list in the PR what was checked; what waits on the player's own session goes in the PR as `/reload` tests for the user.
- Host globals go in `.luacheckrc`; LuaLS gets WoW APIs from the pinned Ketho annotations.
  Add missing Forever/integration APIs with real types in `types/`, never `diagnostics.globals`.
- Every TOC file, including generated data, stays in the LuaLS and multi-value gates.
  Run `tools/typecheck.sh` with LuaLS 3.19.1; it fetches the pinned API annotations on first use.
  Parenthesize scalar `select(...)` in last call/table/return positions; intentional expansion
  needs a trailing `-- multi-value: <reason>`.
- Commits are signed (`git commit -S`) with the personal email.
- Release: load `.agents/skills/release/SKILL.md` when preparing or publishing a release.
  A cloud session cannot push tags: once the version's PR is merged and `.github/workflows/ci.yml` passed on main, start the Release
  workflow on main with `version` (and `commit` for an older main commit); it tags that commit and publishes.
- Quality: read the live roots, settled shapes and anti-patterns in `.sloppatrol/instructions.md` before cleanup,
  dead-code or refactoring work.
- A recipe colour always comes from the game; bundled thresholds only fill in what it does not show.
  Missing data renders `?`, never a guess. A gathering node has no colour in the game: its tooltip colours
  your live skill against the node's waivered requirement with Classic's gathering bands (orange to 25 past
  it, yellow to 50, green to 100). Nodes are matched by their enUS name, so other locales show nothing.
  A corpse (skinning, or herbalism and mining on a corpse) shows `?` until Classic's level rule is confirmed on
  Forever (`CORPSE_RULE_CONFIRMED` in `Core/Model.lua`).
- Never stretch art: an icon, atlas or texture is drawn at its native aspect, through `UI/Art.lua` (`Art.Fit`,
  `Art.Markup`); only nine-slice pieces, bars and fills stretch by design. `tools/lint_art.py` refuses a raw
  setter elsewhere unless its line says why its shape is right: `-- art-ok: <reason>`.
- Store copy, README and posts pitch the addon as looking like it came with the game, in cjber's
  own voice, never AI marketing: `wow-forever-addon` WFA-23/24, checked before every store paste.

## Waivers

- WFA-28: trainer fees, rank fees and their skill and level requirements (`Data/Trainer.lua`): CMaNGOS
  classic-db `npc_trainer`, QuestieDB and AtlasLoot hold no trainer service; a fee read at a trainer's window
  replaces the bundled one.
- WFA-28: which NPC trains which profession and to what cap (`ns.ProfessionTrainers`): CMaNGOS classic-db
  `npc_trainer`, QuestieDB has only an NPC's subtitle and flags and AtlasLoot has no trainers; the trainer's
  name, side and place are QuestieDB's.
- WFA-28: a recipe scroll's drop chances and world-drop marking (`ns.ScrollDrops`, `ns.WorldDrops`): CMaNGOS
  classic-db loot tables, QuestieDB's drop tables cover no recipe scroll and AtlasLoot's rates cover a few
  dungeon bosses; AtlasLoot's rate replaces the bundled one where it has one.
- WFA-28: which gathering skill yields a reagent (`ns.GatheredBy`): CMaNGOS classic-db node, skinning and
  fishing loot, neither database ties an item to a gathering skill.
- WFA-28: which reagents a creature drops often enough to loot (`ns.LootedFrom`): CMaNGOS classic-db
  `creature_loot_template` direct rows and `item_template` classes; QuestieDB's drop tables are read in game,
  not bundled.
- WFA-28: the quest that teaches a profession rank (its reward spell, `ns.RankQuests`): CMaNGOS classic-db
  `quest_template` RewSpell/RewSpellCast; neither the client nor QuestieDB links a quest to the spell it rewards.
  The quest's title and giver are QuestieDB's (owner decision 2026-10-16, delegated).
- WFA-28: a gathering node's required skill (`ns.NodeSkills`): CMaNGOS classic-db `gameobject_template` lock with
  the client's `Lock` DB2; neither database ties a node to a lock (owner decision 2026-10-15).

A scroll's vendor price is in neither database and is not bundled: it is the one seen at a merchant's
window. Which vendor limits an item's stock (CMaNGOS `npc_vendor.maxcount`) is bundled per vendor in
`Data/Sources.lua` as `ns.LimitedStock`. `Data/Recipes.lua`, `Data/Thresholds.lua` and `Data/Vendor.lua` come from the
client's own DB2 tables through wago.tools, not a classic-db dump: they stay as they are.

## Secure UI regression checks

`tools/typecheck.sh` checks the TOC/XML load graph, LuaLS coverage, `tools/lint_secret.py` (secret values through `ns.Readable`, tooltip hooks behind `ns.Usable`), `tools/check_editorconfig.py` and `tools/check_family.py` (the shared family block between the `forever-family` markers in README.md and docs/curseforge.md).
`tools/forever_tools/` is the shared tooling (cjber/forever-core, https://github.com/cjber/forever-core/tree/main/.agents/skills/wow-forever-addon/tooling), vendored byte for byte: never edit it here.
`python3 tools/forever_tools/sync.py check` verifies it offline; `sync.py update --source <checkout>` is the only way to refresh it.
`tools/forever_sim/` is the shared client simulator from the same place, vendored the same way (`python3 tools/forever_sim/sync.py check`, `update --source <checkout>`). `luajit tools/forever_sim/run.lua` runs the scenarios in `tests/sim` under the client's real Blizzard UI source, fetched once with `python3 tools/forever_sim/fetch.py`; `tests/sim/exercise_scenario.lua` opens every slash command, the world map, combat and a `/reload` through `sim:exercise()`.
Never touch Blizzard's Lua state: WFA-38 in `wow-forever-addon` lists what addon code may do to Blizzard's
frames, how to restyle one by drawing on top, and when a `taint-ok` exception holds.
Keep addon tracker sections in the shared column: build one with `ForeverCore.TrackerSection.Create` (`header`,
`show`, `legacy`/`legacyKey`, `safeCall`, `onUnattached`), give its lines `ForeverCore.TrackerLine.SetInteractive`
and its menu entries `AddHeaderMenuEntries`, and never create the frame, attach it or read an anchor by hand. Never
register with Blizzard's tracker manager.
Render only after `PLAYER_ENTERING_WORLD` and `VARIABLES_LOADED`, deferred one frame.
This supersedes WFA-5's native registration guidance. ForeverCore owns the host; native manager access is
forbidden in the integration harness.
Test event ordering and reuse, not just method existence.
